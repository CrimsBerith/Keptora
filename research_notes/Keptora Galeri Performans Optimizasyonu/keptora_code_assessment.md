# Keptora gallery projection assessment

Read-only review of the current worktree. No source or test files changed. The relevant projection/model/test files are already modified in the worktree, so findings describe the current snapshot, not an asserted clean-branch baseline.

## Executive assessment

- **Sorting is not proven to dominate.** The iOS 50k test's default criteria do not sort; it measures filtering plus month-section creation and review projection. The Mac 50k builder does sort, but no retained Mac timing or phase breakdown was found. Total-time results cannot isolate sort cost. [iOS criteria and builder](../../KeptoraiOS/UI/MobileArchiveView.swift#L7-L22) [iOS 50k test](../../KeptoraiOSTests/GalleryPerformanceTests.swift#L24-L44) [Mac builder](../../Keptora/Features/Home/MacLibraryServices.swift#L143-L192) [Mac 50k test](../../KeptoraTests/MacArchiveModelTests.swift#L137-L176)
- **Production builders execute off MainActor; their input preparation does not.** Both UI/model paths gather projection inputs on MainActor, then use a detached task for the builder. The XCTest methods call the builders synchronously from `@MainActor` test classes; they do not exercise that production scheduling boundary. [iOS update path](../../KeptoraiOS/UI/MobileArchiveView.swift#L455-L507) [Mac update path](../../Keptora/Features/Home/MacArchiveModel.swift#L68-L112) [test actor isolation](../../KeptoraiOSTests/GalleryPerformanceTests.swift#L7-L9) [Mac test actor isolation](../../KeptoraTests/MacArchiveModelTests.swift#L1-L6)
- **Next step should be phase-separated measurements and semantic regression tests, not sort/index caching.** MainActor input snapshot costs, per-stage CPU, allocations, UI apply/diff, and frame hitches are not measured by the existing 50k cases.

## What the 50k tests measure

### iOS

`testGalleryProjectionComputationFor50kItems` creates 50,000 synthetic `UniversalMediaAsset`s before entering `measure`; fixture creation is excluded from the timed block. The test sets only `criteria.media = 1`, passes empty review groups and quality assessments, and measures one synchronous call to `MobileGalleryProjectionBuilder.build(input)` using `XCTClockMetric`. It asserts 45,000 visible photos after timing. It does not time the `Task.detached` wrapper, actor handoff, input construction, view rendering, image work, or scrolling. [fixture and test](../../KeptoraiOSTests/GalleryPerformanceTests.swift#L7-L44)

Default `oldestFirst` and `largestFirst` are false, while `grouping` defaults to month. Therefore this case filters 50k to 45k, preserves source order, groups those results by month, builds empty-group review blocks, and creates IDs/maps; **it does not execute the builder's sort branch**. [criteria defaults](../../KeptoraiOS/UI/MobileArchiveView.swift#L7-L22) [filter/order/build stages](../../KeptoraiOS/UI/MobileArchiveView.swift#L107-L174) [section construction](../../KeptoraiOS/UI/MobileArchiveView.swift#L191-L215)

The test named `testGalleryProjectionFiltersSortsAndGroupsOffscreenAssets` uses 20 assets and checks a small oldest-first/collection/finding fixture, one section, and review membership as a set. It does not check keeper badges, candidates, deterministic order of review output, or broad filter combinations. The cancellation test starts with 2,000 assets, cancels immediately inside a detached task, and expects `nil`; it does not prove cancellation responsiveness after significant work or during sort/review-map construction. [iOS focused tests](../../KeptoraiOSTests/GalleryPerformanceTests.swift#L46-L88)

### macOS

`testMacGalleryProjectionComputationFor50kItems` also creates its 50,000-item synthetic fixture outside `measure`, then measures the synchronous `MacGalleryProjection.build(input)` call with `XCTClockMetric` and asserts 45,000 visible items. Its fixture sets media to photos; context otherwise defaults to smart order, and the builder unconditionally sorts visible items newest-first (capture/creation date, then ID). It also builds review blocks, membership, scope IDs, finding/quality counts, issue mapping, and keeper/candidate projections. The test has no assertions about order or other projection fields. [Mac context defaults](../../Keptora/Features/Home/MacArchiveModel.swift#L19-L31) [Mac builder](../../Keptora/Features/Home/MacLibraryServices.swift#L143-L192) [Mac 50k test](../../KeptoraTests/MacArchiveModelTests.swift#L137-L176)

`testThreeThousandItemProjectionIsReusedDuringSelectionAndProgress` checks that selection/progress changes do not increment the model's projection-build counter, and a media-filter change increments it once. It is a cache/reuse behavior check, not a timing test. [Mac reuse test](../../KeptoraTests/MacArchiveModelTests.swift#L122-L135)

## Cost map: measured, inferred, and still on MainActor

### Measured

- Existing 50k tests time the complete synchronous builder, not individual phases. iOS's timed default case excludes sorting; Mac's includes its date sort. Neither reports allocations, peak memory, actor responsiveness, frame time, or scroll smoothness. [iOS benchmark](../../KeptoraiOSTests/GalleryPerformanceTests.swift#L24-L44) [Mac benchmark](../../KeptoraTests/MacArchiveModelTests.swift#L137-L176)
- The only available numerical timing is the prior iOS simulator summary above. It cannot establish Mac performance or sort share.

### Inferred work / plausible hotspots

- **iOS filtering:** one pass over the full input applies finding IDs, media, album, favourite, collection, date, and search predicates. The 50k test exercises media filtering, but not search, album, date, favorites, or populated finding IDs. [iOS builder](../../KeptoraiOS/UI/MobileArchiveView.swift#L107-L131)
- **Sorting varies by state:** iOS size-sort performs `sort` with descending bytes (missing size as `-1`), then descending date and ascending ID ties; oldest-first reverses input order. Mac always sorts by descending capture/creation date and ascending ID ties. These are different workloads; replacing them with a shared/pre-sorted index could change output order or missing-value/tie behavior. [iOS order logic](../../KeptoraiOS/UI/MobileArchiveView.swift#L132-L145) [Mac order logic](../../Keptora/Features/Home/MacLibraryServices.swift#L160-L166)
- **Maps, sets, and arrays:** iOS sections accumulate per-section arrays; `LibraryReviewBlock.make` builds a lookup from mapped assets; the builder separately traverses groups for membership, maps visible IDs into a `Set`, flattens review assets/groups, and computes keeper badges/candidates. Mac likewise creates review blocks and related-membership maps, maps assets into scope IDs and issues, and computes counts. These allocate and traverse data, but present measurements do not rank their cost against filtering or sorting. [iOS builder](../../KeptoraiOS/UI/MobileArchiveView.swift#L146-L174) [Mac builder](../../Keptora/Features/Home/MacLibraryServices.swift#L167-L192) [review block and decision helpers](../../Packages/KeptoraCore/Sources/KeptoraCore/AnalysisModels.swift#L241-L340)
- **Possible repeat work outside the builder:** Mobile collection rows build filtered arrays, and the “Videos by Size” row sorts its filtered videos. Mac selection/review UI maps visible IDs or constructs visible scopes and filters candidates. Their actual redraw frequency/cost needs profiling before attributing it to the projection builder. [iOS collection rows](../../KeptoraiOS/UI/MobileArchiveView.swift#L1726-L1733) [Mac visible-ID work](../../Keptora/Features/Home/MacArchiveView.swift#L260-L267) [Mac review scopes](../../Keptora/Features/Home/MacArchiveView.swift#L546-L568)

### Synchronous work that remains on MainActor

- iOS `updateGalleryProjection` reads `store.scopedAssets`, collection state, review groups, quality, and decisions to assemble the `Sendable` input before creating `Task.detached`. On a cold scoped-assets cache, `scopedAssets` calls `LibrarySourceCatalogue.assets`, which builds a latest-assets dictionary, filters sources, flattens batches, and deduplicates. This potentially O(N) preparation is outside the worker and outside the 50k builder benchmark. [iOS update path](../../KeptoraiOS/UI/MobileArchiveView.swift#L469-L483) [iOS scope cache](../../KeptoraiOS/App/MobileKeptoraStore.swift#L219-L227) [catalogue implementation](../../Packages/KeptoraCore/Sources/KeptoraCore/LibraryWorkflow.swift#L120-L140)
- macOS `invalidateGalleryProjection` similarly snapshots `scopedAssets`, `reviewGroups`, quality, issues, decisions, context, and search in the `@MainActor` model before launching detached work. Cold `scopedAssets` uses the same catalogue operation; `reviewGroups` may be composed/cached on first access. The 20 ms debounce is also in the actor task but is not part of the static builder's benchmark. [Mac invalidation/snapshot/worker](../../Keptora/Features/Home/MacArchiveModel.swift#L68-L112) [Mac scoped assets and groups](../../Keptora/Features/Home/MacArchiveModel.swift#L218-L239)
- Applying the completed projection updates published SwiftUI state on MainActor. The 50k unit tests bypass both production orchestration paths, so they cannot show whether a busy MainActor remains responsive or whether the published projection causes expensive view diff/layout work. [iOS result apply](../../KeptoraiOS/UI/MobileArchiveView.swift#L469-L491) [Mac result apply](../../Keptora/Features/Home/MacArchiveModel.swift#L80-L112)

## Cache dependencies and behavior risks

- iOS request identity includes store `galleryRevision`, filter criteria, and debounced search. Revision is bumped for assets/scope, review groups, quality assessments, decisions, and collection IDs/kind/size-sort; source-selection changes invalidate scope. These dependencies should remain covered if projections or intermediate indexes are cached. [iOS request](../../KeptoraiOS/UI/MobileArchiveView.swift#L457-L465) [store invalidation paths](../../KeptoraiOS/App/MobileKeptoraStore.swift#L77-L103) [collection and quality/decision revisions](../../KeptoraiOS/App/MobileKeptoraStore.swift#L159-L166) [source selection](../../KeptoraiOS/App/MobileKeptoraStore.swift#L238-L246) [quality/decision revisions](../../KeptoraiOS/App/MobileKeptoraStore.swift#L496-L501)
- macOS invalidates on assets/scope, group changes, context changes, final analysis updates, quality/issues outside active analysis, and decisions. Search is applied after debounce. Cache/index keys must cover the full asset metadata used by filters/sorts, groups, quality/issues, decisions/protected IDs, and context—not just count or IDs. [Mac invalidation paths](../../Keptora/Features/Home/MacArchiveModel.swift#L68-L145) [group and decision observers](../../Keptora/Features/Home/MacArchiveModel.swift#L218-L301) [analysis completion invalidation](../../Keptora/Features/Home/MacArchiveModel.swift#L735-L740)
- Preserve exact order semantics: iOS default preserves catalogue order; `oldestFirst` reverses that order rather than explicitly sorting by date; size ordering handles absent sizes as `-1` and uses date/ID tie-breaks. Mac uses date/ID ordering. Section boundaries depend on `Calendar.current` and month/day grouping. [criteria defaults](../../KeptoraiOS/UI/MobileArchiveView.swift#L7-L22) [iOS order and sections](../../KeptoraiOS/UI/MobileArchiveView.swift#L132-L215) [Mac comparator](../../Keptora/Features/Home/MacLibraryServices.swift#L160-L166)
- Preserve review semantics as well as visible IDs: connected/overlapping groups, user keepers, suggested keepers, protected IDs, quality, and candidate exclusions affect review blocks and cleanup recommendations. Current iOS small test checks membership IDs only, not keeper/candidate output; Mac 50k test checks only count. Cache changes need explicit assertions for both order and review decisions. [review construction](../../KeptoraiOS/UI/MobileArchiveView.swift#L149-L174) [keeper/candidate implementation](../../Packages/KeptoraCore/Sources/KeptoraCore/AnalysisModels.swift#L241-L290) [block construction](../../Packages/KeptoraCore/Sources/KeptoraCore/AnalysisModels.swift#L316-L340)

## Ranked experiments before sort/index caching

1. **Lock down projection equivalence with small adversarial fixtures.** Add/execute focused cases covering equal/missing dates and sizes, ID tie-breaks, oldest-first reversal, ascending source order, day/month/ungrouped sections, date endpoints, search, collection kinds, album/favourite filters, and duplicate/overlapping review groups. Assert ordered IDs, sections, blocks, keeper badges, and candidate IDs—not just counts or sets. Run same scenarios on macOS and iOS where semantics are intended to match. Existing tests are too sparse to detect index/cache order drift. [iOS projection tests](../../KeptoraiOSTests/GalleryPerformanceTests.swift#L46-L88) [Mac projection test](../../KeptoraTests/MacArchiveModelTests.swift#L137-L176)
2. **Measure builder phases separately on both platforms.** Use representative 50k data and record filter-only, each sort mode, sectioning, review-block/map/candidate construction, and full-build times; include warm-up and repeated samples. Compare iOS default/no-sort against largest-first and Mac's always-sort path. This directly tests sort dominance instead of inferring it from one total. Add memory/allocation measurement because current benchmarks only use `XCTClockMetric`.
3. **Measure MainActor snapshot and responsiveness.** Profile cold and warm `scopedAssets`/`reviewGroups` input assembly separately from detached work and result application. During a production-path 50k refresh, record MainActor scheduling delay and UI frame hitches; test stale-request cancellation and repeated rapid filter changes. The immediate-cancel unit test is not a responsiveness bound.
4. **Run Instruments against realistic local synthetic libraries.** On physical iPhone and representative Mac, capture Time Profiler/Points of Interest, Allocations, and SwiftUI/Core Animation frame-hitch data during initial load, filter changes, size-sort, search, and scroll. Keep a reproducible 50k synthetic fixture and retain `.xcresult`/trace plus device, OS, sample count, warm/cold state. Do not treat simulator-only UI timing as physical-device FPS evidence.
5. **Exercise invalidation matrix before introducing cached indexes.** For each dependency (assets and source scope, each filter/search input, collection sort/kind/IDs, groups, quality, issues, keeper/protection decisions), mutate just that value and verify recompute; also verify irrelevant selection/progress changes do not recompute. Add calendar/time-zone-sensitive section checks if section results are cached. Existing Mac test covers only selection/progress reuse and media-filter invalidation; iOS currently has no comparable revision-matrix test. [Mac reuse test](../../KeptoraTests/MacArchiveModelTests.swift#L122-L135) [iOS revision/request dependencies](../../KeptoraiOS/UI/MobileArchiveView.swift#L457-L465)

**Decision gate:** Only consider sort/index caching after phase measurements show a repeatable, material sort/index share, equivalence tests pass for tie/missing-value and keeper behavior, and measured invalidation coverage prevents stale projections. Current evidence does not meet that gate.
